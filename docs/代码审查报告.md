# akaLinkPro 代码审查报告

**审查范围**：`firmware/application_5301` 全部自有代码（DAP/SWD/JTAG 引擎、RTT 桥、J-Scope 采样器、USB 复合层、CDC、HID、RISC-V 引擎、api/main/led/flash/EasyFlash port）、`firmware/bootloader_dfu` 全部、`script_test` 两个旗舰脚本精读 + `docs/index.html` 抽查。vendored 第三方（EasyFlash src/、SEGGER RTT、汇编 blob 逐指令级）只审了集成点。所有 P1 级发现我都在源码里亲自复核过行号与代码。

**总体结论**：工程质量明显高于典型参考实现移植——注释里保留实测数据与踩坑记录、关键不变量（先交付再推进 RdOff、管线三不变量、缓冲池绝不复用在飞缓冲）落实到位、bootloader 的 flash 边界防护扎实。但暴露出一个系统性模式：**“信任边界”和“时序边界”上的单点遗漏**——上游 CMSIS-DAP 的无界计数在 WebUSB 暴露面下从理论风险变成现实攻击面，本地新代码则在影子缓存、raw 透传、标定路径上各有一次漏防。

## P1 —— 建议优先修（内存安全 / 静默数据错乱）

**1. DAP 主机命令可越界写响应缓冲（上游继承，攻击面在 WebUSB）**
`DAP.c:1950-1996`（TransferBlock）：`request_count` 取自主机 16 位字段，读方向每个计数写 4 字节进 `USB_Response[4][1024]`，无任何上限——声称 count=0xFFFF 的一条 bulk 请求即可线性写穿约 256 KB 静态区。同类：`DAP.c:896`（DAP_Transfer，count≤255 × 带 TIMESTAMP 最多 8 字节/项 = 2040 B）、`DAP.c:560` 起（SWD/JTAG Sequence，累计响应可达 2041 B）、`DAP.c:2611`（ExecuteCommands 循环累加无界）。上游把“主机可信”当设计前提，但本固件带 WebUSB/WinUSB 接口，浏览器页面就能发任意 bulk 数据。修复：各 handler 把计数钳到剩余缓冲（每处 3-5 行）。

**2. DAP_JTAG_Configure 设备数无上限**
`DAP.c:720-735`：`count = *request++` 直接作为 `jtag_dev.ir_length/ir_before/ir_after[]`（各 8 项）的循环上限，count=255 时越界写约 765 字节并破坏 `DAP_Data` 邻接全局状态。一行修：`count > DAP_JTAG_DEV_CNT` 则返回 DAP_ERROR。

**3. HID RTT raw 透传：24 字节响应缓冲可被同一引擎打穿 + 漏作废影子缓存**
`rtt_bridge.c:884-893`：`DAP_ExecuteCommand(s_raw_req, s_raw_rsp)` 的响应缓冲只有 24 字节——raw 请求首字节发 `0x7F`（ExecuteCommands）或一条大 count Transfer，响应就远超 24 B，越界覆盖邻接静态变量（`s_start_pending` 等）。另外这是**唯一**“主机碰 DAP”却既不调 `rtt_bridge_note_dap_activity()` 也不刷新 `s_last_dap` 的入口（主通路 `chry_dap_handle` 每条命令都调），主机经它写了 DP_SELECT/AP_CSW 后，scope/RTT 还拿旧影子缓存 → 静默读错地址。修复：执行前后各加一次 `note_dap_activity()`，并把 raw 通道限制为单命令或扩缓冲到 `DAP_XFER_SIZE`。

**4. `scope_run_bench()` 在无空闲缓冲时指针越界（本次新发现）**
`scope_sampler.c:644-646`：`uint8_t *dst = &s_pkt[s_fill_buf][SCOPE_HDR];` 在函数入口无条件取址，而 `s_fill_buf` 合法值含哨兵 `0xFF`（“没有缓冲”）。8 个包缓冲全部在飞（例如主机停止读 0x83 后停采样，再点 action 8 标定）时，`s_pkt[255]` 是越界指针，`scope_sample_bytes()` 随后按 `iters`（上限 100000）× 帧字节往里写——持续的越界写。修复：取址移到 `s_fill_buf < SCOPE_TX_BUFS` 判断之后，或先 `scope_alloc_buf()`。

**5. `swd_write_ap` 影子缓存在传输成功之前更新（J-Scope 新代码）**
`swd_host.c:259-288`：`case AP_CSW: dap_state.csw = val;` / `case AP_TAR: dap_state.tarp = val; tarp_ok = 1U;` 都在 `swd_transfer_retry` **之前**执行，失败路径 `return 0` 不回滚。下一次调用看到缓存命中就跳过写入，而硬件里还是旧值——瞬时 WAIT/FAULT 一次之后，`swd_read_word_hold_prepare()` 以为“抱住了 TAR”，实际 TAR 已被自增带跑，**采样数据静默错位**（不报错、看起来正常）。修复：缓存更新移到传输+RDBUFF 确认成功之后，失败分支顺手 `swd_invalidate_ap_cache()`。对照 `swd_write_dp`（212-214 行）就是只在成功后更新的正确写法。

**6. `DAP.c:1066` 拆分 SWD_Transfer 时漏改的调用点**
`response_value = SWD_Write(DP_RDBUFF | DAP_TRANSFER_RnW, &data);` —— 把 RnW=1 的读请求喂给了写引擎：ACK 后主机照样强驱 SWDIO 数据相位（与目标争总线，靠串联电阻苟活），且 `data` 是未初始化栈值，作为“上一笔 posted 读结果”进响应。同源问题 `DAP.c:1387`（JTAG 版）。上游此处是统一的 `SWD_Transfer()` 按 RnW 分派。修复：分别改 `SWD_Read(...)` / `JTAG_Read(...)`。

## P2 —— 边界情形 bug / 可靠性

**7. `rtt_bridge_stop()` 恢复 UART 数据源不做 resync（本次新发现）**
`cdc_interface.c:113-120`：`uartx_set_cdc_source(0)` 只清标志。桥运行期间 UART RX DMA 一直 infinite-loop 转着（`rb_write_pos` 停在旧值），停桥后第一次 flush（`uartx_rx_flush_locked`）把期间攒下的字节——长时间桥接后可能超一整圈、是任意陈旧混合——一次性灌进 CDC 环送给主机。对照：`chry_dap_usb2uart_set_enabled(1)` 的恢复路径就调了 `uartx_rx_resync()`（`usb_composite.c:851`），这条路没有。修复：`rtt_bridge_stop` 恢复源时同样 resync。

**8. `rtt_swd_set_clock` 判错下标错误**
`rtt_bridge.c:220`：`return (s_resp[2] == DAP_OK)`——SWJ_Clock 的状态在 `s_resp[1]`；`s_resp[2]` 靠静态零初始化“恰好等于 DAP_OK”恒判成功，真正的失败会被漏判（连 `-1` 都不报，斜坡逻辑失去失败感知）。

**9. JTAG_Sequence 硬编码 45M blob、delay 恒 0**
`JTAG_DP.c:43`：`JTAG_Sequence_GPIO_ASM_45M(info, tdi, tdo, 0)` 完全无视 `DAP_Data.clock_delay`，`JTAG_Sequence_Slow` 是死代码。低速 JTAG 目标的 TAP 复位/IR 扫描（都走 sequence）会以 ~45M 时序跑，失步风险；README 把“`adapter speed` 对 JTAG 无效”记为已知坑，但这是缺陷不是特性（SWD 侧同一问题已经用档位分派修好了）。

**10. SWD 主机通路 bit-bang 无中断保护（子代理发现，待验证）**
`swd_host_port.c:54-62` 只有 swd_host 通路（桥/采样器）用 `disable_global_irq` 包住位翻转；DAP 主机通路 `DAP.c → SWD_Read/SWD_Write` 直调 blob 无保护，blob 内部的 `csrrci` 已被注释（`SW_DP_GPIO_ASM_SLOW.S:164`）。36 MHz+ 档主机 bulk 传输被 USB/CDC ISR 打断时 ACK 采样错位，与桥/采样器可靠性不一致。建议把临界区下沉到 `SWD_Read/SWD_Write` 让两条通路共享。

**11. USB RESET 后 DAP 队列索引不复位（本次新发现）**
`usb_composite.c:447-487`：RESET 事件只清 3 个 idle 标志，`USB_RequestIndexI/O`、`USB_RequestCountI/O` 及 Response 侧四个计数全部保留；而 CONFIGURED 固定武装 `USB_Request[0]`。运行中总线复位（主机驱动重初始化、睡眠唤醒）后，`dap_out_callback` 用旧 `IndexI` 做 TransferAbort 判断（读的是旧缓冲），数据却落在 [0]——DAP 命令流错乱直到再次复位。修复：RESET 时把两组 index/count 全部清零。

**12. `usbd_ep_start_write` 返回值全程忽略**
`usb_composite.c`（CDC IN，561-580、899-910）与 `scope_sampler.c`（316-320、362-366、391-397）：端点写失败（断开、stall）无任何反馈——CDC 侧 `usbtx_idle_flag` 卡 0 永久停流；scope 侧 FIFO（`s_if_count`）与真实在飞脱钩。现有的“丢拍缓解”只覆盖缓冲忙，不覆盖 start_write 本身失败。至少在 `scope_push_packet` 检查返回值并回滚 `s_if_count`/`s_tx_busy`。USB 重新枚举时 armed 的 0x83 传输不完成、8 个缓冲永久泄漏也属同类（表现为重枚举后 usb_drop 狂涨，STOP/START 可恢复）。

**13. `vfat.c` fat_next 无界读（bootloader，恶意/垃圾 FAT 链）**
`vfat.c:326-332`：`s_fat1[cluster * 2]` 对 cluster>255（s_fat1 只有 512 B）越界读，cluster 来自主机写的 FAT/根目录项。正常拖入的固件用簇 5..36 无碍；恶意链值可读越界最多 ~128 KB 静态区。修复：`cluster > 255` 直接返回终止符。flash 写入路径本身我核对过是安全的：`APP_MAX_SIZE` 双重钳制 + erase 上界，参数区（0x800FE000 起）和 bootloader 都不可能被 MSC/DFU 写到。

## P3 —— 择要

- **`scope_sampler_configure` 在 USB ISR 里先重建计划、后停运行**（`scope_sampler.c:741→759`）：运行中改配置存在几个采样拍的新旧混用窗口，应先 `s_running=0` 再改。
- **`scope_start_now` memset `s_tx_busy`**（`scope_sampler.c:621`）不等待在飞传输排空，快速 STOP→START 且主机暂停读时可能复用 DMA 仍在读的缓冲。
- **APP 侧 `msc_interface.c` 是“假盘”**（10 扇区 RAM、`get_cap` 谎报 1000、≥10 扇区静默丢写返回成功）——当前 `CONFIG_CHERRYDAP_USE_MSC=0` 未编译，但留着是坑，建议删除或加注释封条。
- **VREF ADC 疑似从未触发转换**（`led_state.c:156` 只 `adc16_get_oneshot_result`，全文件无 oneshot trigger）→ `CMD_GET_VOLTAGE` 可能恒 0，待在 akaLinkPro 板上验证（EVKLite 无此电路不受影响）。
- **bootloader “签名”实为 magic + CRC32**（`hpm_dfu_trigger.c` boot 版）：防损坏有效、不防恶意固件；README“APP 带签名”措辞容易让人以为是密码学签名，建议文档写明。
- **vfat 升级错误标志粘滞**：同一起始簇重写文件不清 `s_upgrade_error`，出错后基本只能重插。

## 判定不修（附理由）

- **#10 DAP 通路无临界区**：前提要更正 —— `SWD_Transfer()` 本身**有**临界区，问题是 `DAP.c` 里几十处**绕过**它直调 `SWD_Read/SWD_Write`，而 `chry_dap_handle()` 跑在 main 循环（`main.c:101`）而非 ISR。但实测 60 MHz 下 20 KB 读写全程 `verified`、xfer 3372/2989 KB/s，无可观测损伤。**建议先做对照实验**（CDC 满速 + 60M DAP 读写看错误率），有差异再把临界区下沉。
- **#1/#2 计数钳位**：攻击面我们不在乎，但脚本这类"随便发 DAP 请求"的逃生口手滑一次就能写穿静态区，合计约 10 行。**建议顺手做**，本轮未做。
- **#9 JTAG 恒 45M**、**#13 vfat 越界读**：前者只咬低速 JTAG 目标（手上全是高速的），且改法要先确认 blob 的 delay 语义；后者只在 FAT 链写坏时触发。排下个迭代。
- **#12 CDC 侧**：**不需要修**。CONFIGURED 分支（`usb_composite.c:474-477`）在已有 line coding 时置 `config_uart`，而 `chry_dap_usb2uart_handle()` 的 `config_uart` 分支里显式 `usbtx_idle_flag = 1`（`:881`）重新武装 —— 复位后 CDC 能自愈。
- **P3 各条**：假 MSC（未编译）、VREF ADC（EVKLite 无此电路）、APP 无看门狗、两处 `"cfg"` 硬编码、MSC 接口号硬编码、`scope_sampler_configure` 先建计划后停运行、`scope_start_now` memset `s_tx_busy` —— 维持"留着"的判断。

## 本轮新发现（原报告没有的）

**N1. DWC2 端点只认一笔在飞传输，后启动的会静默顶掉前一笔 —— 8 个包缓冲会漏。**
证据：`scope_bench_nobuf_test.py` 里连续推了 8 个包（全部"在飞"），主机开始读时**只排出来 512 B（1 个包）**。
根因在 SDK：`usb_device_edpt_xfer()`（`hpm_usb_device.c:248`）每次都用 `qtd[ep_idx*N + 0]` 并重挂
`qhd->attached_qtd` / `qtd_overlay.next`，而它的 `bool` 返回值被移植层 `usbd_ep_start_write()` 丢掉了 ——
所以 `scope_sampler.c` 注释里记的"端点忙时静默不启动"，本质是**前一笔被顶掉**：那一笔的完成回调永远不会来，
缓冲永久占住，只能 STOP/START 恢复。我们测到的"USB 缓冲耗尽"丢拍里，有一部分其实是被顶掉而不是没发。
**修法**：把 8 个缓冲做成真正的发送队列 —— 只在没有在飞传输时启动，其余排队，由完成回调接着启动下一包（约 20 行）。
收益是不再静默丢包/漏缓冲；代价是主机瞬时变慢时从"漏缓冲"变成"如实丢拍"，需复测 3 µs 与 pack 两档。**本轮未做。**

**N2. raw 通道上的 SWJ_Sequence line reset 之后链路不应答（根因未明）。**
证据（`dap_raw_boundary_test.py --diag`）：裸读 IDCODE = `0x1BA01477`（正常）→ `DAP_Connect` 后仍正常 →
**发 51 拍 line reset 后 IDCODE 变 ACK=7**（总线上没人应答）→ 再发一次 jtag-to-swd（0xE79E）又能读回。
OpenOCD 自己的连接不受影响（本轮 8 个档位全部 `verified`），范围限于 raw 通道；测试脚本已改成
"假定探针侧已初始化链路"，不再发这条序列。怀疑方向：序列 blob 的输出极性/字节序，或
`PIN_SWDIO_OUT_ENABLE()` 在该 port 上的行为。
